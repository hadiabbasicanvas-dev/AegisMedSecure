## 1. Introduction

### 1.1 Purpose
The purpose of this Software Requirements Specification (SRS) document is to define the functional, non-functional, interface, and behavioral requirements for **Aegis Guardian AI**, an autonomous AI-driven healthcare Security Operations Center (SOC) and Security Orchestration, Automation, and Response (SOAR) platform. Aegis Guardian AI is designed to continuously monitor healthcare IT and Medical IoT (IoMT) networks, detect complex zero-day and multi-stage cyber threats using machine learning and Large Language Models (OpenAI GPT-4o), dynamically score security risks, and execute automated, millisecond-level containment actions to safeguard critical hospital subnets.

### 1.2 Scope
Aegis Guardian AI provides comprehensive digital monitoring across the entire technological infrastructure of Quaid-e-Azam International Hospital (QIH). The monitored scope encompasses:
* **Core Clinical Systems:** Electronic Medical Records (EMR), Hospital Information System (HMS), Laboratory Information System (LIS), and Picture Archiving and Communication System (PACS/RIS).
* **Diagnostic Imaging Infrastructure:** MRI, CT Scanner, X-Ray, Mammography, and Ultrasound workstations.
* **Clinical Care & Auxiliary Services:** Emergency Trauma Center, Inpatient Department (IPD), Outpatient Department (OPD), Dialysis Unit, Blood Bank, and Central Pharmacy Management.
* **Critical Life-Support Networks:** Intensive Care Units including Adult ICU, Neonatal ICU (NICU), and Pediatric ICU (PICU).
* **Administrative & Financial Networks:** Patient Billing, OPD Registration, Staff HR Portal, Central Email/Communication Servers, CCTV Security Subnets, and Cloud Backup Repositories.

## 4. System Capabilities & Functional Requirements (FR)

### Module 1: Authentication & Zero-Trust Access

#### FR-001: Zero-Trust Authentication & Multi-Factor Auth
* **Description:** The system shall authenticate all users requesting access to Aegis Guardian AI using JSON Web Tokens (JWT) and multi-factor authentication (MFA).
* **Inputs:** Username/Email, Password, MFA OTP Code.
* **Outputs:** Auth Token (JWT), Refresh Token, User Session State.
* **Preconditions:** User account exists and status is ACTIVE.
* **Postconditions:** User identity is verified, session timestamp is recorded in Audit Log.
* **Acceptance Criteria:** Passwords must be hashed using bcrypt (cost factor >= 12); failed logins must lock after 5 attempts.
* **Priority:** High

#### FR-002: Role-Based Access Enforcement
* **Description:** The system shall restrict user access to dashboard screens, API endpoints, and actions based on assigned user roles.
* **Inputs:** User Session JWT, Requested API Endpoint/Resource ID.
* **Outputs:** Access Granted HTTP 200 / Access Denied HTTP 403.
* **Preconditions:** Valid active user session token provided in request header.
* **Postconditions:** Unallowed actions are blocked and recorded in security logs.
* **Acceptance Criteria:** Non-Super Administrators attempting to invoke kill-switch controls must receive an immediate 403 Forbidden response.
* **Priority:** High

---

### Module 2: Executive SOC Dashboard

#### FR-003: Real-Time Security Posture Score Widget
* **Description:** The system shall compute and render a dynamic global Network Health & Risk Score (0-100) on the main SOC dashboard updated in real-time.
* **Inputs:** Active unresolved alerts, host criticality weights (e.g., ICU = 1.0, Admin = 0.2), network telemetry velocity.
* **Outputs:** Animated visual risk gauge, status badge (HEALTHY, WARNING, CRITICAL).
* **Preconditions:** System background aggregation workers running.
* **Postconditions:** Dashboard UI updates within 1 second of threat event state change.
* **Acceptance Criteria:** A Critical alert on an ICU subnet host must reduce the global health score by at least 25 points immediately.
* **Priority:** High

#### FR-004: Interactive Threat Topology Map
* **Description:** The system shall display an interactive visual topology map representing QIH subnets (ICU, PACS, EMR, OPD, Pharmacy) with active threat indicators.
* **Inputs:** Network subnet mapping configurations, host status metrics.
* **Outputs:** Rendered graph visualization displaying nodes, connections, and pulse animations for compromised assets.
* **Preconditions:** Department and subnet assets registered in database.
* **Postconditions:** User clicking node opens asset detail sidebar with live metrics.
* **Acceptance Criteria:** Compromised nodes must flash red with pulsating animation adhering to brand color `#00A8E8` accenting.
* **Priority:** Medium

---

### Module 3: Live Threat Monitoring & Telemetry Ingestion

#### FR-005: Multi-Source Telemetry Ingestion Pipeline
* **Description:** The system shall ingest simulated network traffic, Syslog streams, WAF logs, and endpoint agent telemetry at up to 5,000 events/second.
* **Inputs:** Raw log strings, JSON telemetry payloads, NetFlow packets.
* **Outputs:** Structured log objects stored in database/memory buffer for correlation.
* **Preconditions:** Ingestion API endpoints active and buffer queues initialized.
* **Postconditions:** Normalized log entries enriched with timestamp, source IP, host criticality, and subnet tag.
* **Acceptance Criteria:** System ingestion latency must remain under 200 milliseconds per batch.
* **Priority:** High

---

### Module 4: Threat Detection & Correlation Engine

#### FR-006: Rule-Based & Anomaly Detection Trigger
* **Description:** The system shall evaluate ingested log telemetry against pre-configured threat signatures and behavioral anomaly thresholds.
* **Inputs:** Normalized log stream.
* **Outputs:** Candidate Threat Events with initial severity tags.
* **Preconditions:** Detection rules active in database.
* **Postconditions:** Threat events passing threshold are routed to AI Threat Analysis Module.
* **Acceptance Criteria:** Detection engine must evaluate logs without dropping packets under normal simulated load.
* **Priority:** High

---

### Module 5: AI Threat Analysis & OpenAI GPT-4o Integration

#### FR-007: Generative AI Root Cause & Confidence Scoring
* **Description:** The system shall submit high-severity threat logs to the OpenAI GPT-4o API engine to synthesize plain-language attack summaries and assign an AI confidence score (0-100%).
* **Inputs:** Anomaly log payload, target system context, historical alert vector.
* **Outputs:** Plain-language threat analysis report, root cause identification, confidence score, recommended mitigation steps.
* **Preconditions:** Valid OpenAI API Key configured in global settings.
* **Postconditions:** Threat alert record enriched with AI analysis fields.
* **Acceptance Criteria:** Response from OpenAI API must be received and displayed within 3 seconds; fallback to local heuristic engine if API fails.
* **Priority:** High

---

### Module 6: Autonomous SOAR Incident Response

#### FR-008: Automated Micro-Segmentation & Quarantine Response
* **Description:** The system shall automatically execute pre-approved containment actions for threats exceeding defined severity thresholds.
* **Inputs:** Validated Threat Alert, SOAR Automation Rules, Subnet Risk Policy.
* **Outputs:** Isolation status change, Firewall routing table update signal, execution log.
* **Preconditions:** SOAR global automation toggle enabled (or Super Admin manual override).
* **Postconditions:** Compromised host moved to Virtual Quarantine VLAN; active network sockets terminated.
* **Acceptance Criteria:** Autonomous quarantine of Critical threats must complete in under 500 milliseconds from detection.
* **Priority:** High

---

### Module 7: Self-Healing & Restoration Engine

#### FR-009: Automated System Restoration & Configuration Reversion
* **Description:** Following threat neutralization, the system shall provide automated workflows to revert modified configurations and restore normal network routing to quarantined assets.
* **Inputs:** Quarantined Asset ID, Analyst Clean Bill of Health Certificate.
* **Outputs:** Restored routing policy, system state reset to HEALTHY.
* **Preconditions:** Threat marked as RESOLVED or MITIGATED by SOC personnel.
* **Postconditions:** Asset removed from Quarantine VLAN; baseline telemetry monitoring resumed.
* **Acceptance Criteria:** Restoration action must require explicit approval from SOC Manager or Super Admin.
* **Priority:** Medium

---

### Module 8: Incident Reporting & Export Generator

#### FR-010: Automated Forensic PDF & Markdown Report Compilation
* **Description:** The system shall generate comprehensive forensic incident summary reports formatted for HIPAA compliance and technical security audits.
* **Inputs:** Incident ID, Audit trail timeline, AI analysis summary, Analyst notes.
* **Outputs:** Downloadable PDF / Markdown report containing branded header, timeline chart, and root-cause analysis.
* **Preconditions:** Incident state set to CLOSED or RESOLVED.
* **Postconditions:** Generated report file saved in secure storage with unique hash.
* **Acceptance Criteria:** Reports must include QIH branding, document metadata, and immutable timestamp hash.
* **Priority:** Medium

* **Outputs:** Recharts interactive line graphs, pie charts, and bar charts.
* **Preconditions:** Historical data available in PostgreSQL database.
* **Postconditions:** Charts update dynamically based on user filter selections.

* **Inputs:** New Threat Alert event trigger.

### Module 11: Immutable Audit Logging

#### FR-013: Tamper-Evident Security Audit Trail
* **Description:** The system shall maintain an immutable, append-only audit trail recording every user login, configuration change, manual override, and SOAR response action.
* **Inputs:** System Action Context (User ID, Action Code, Resource ID, IP Address, Timestamp).

## 5. Non-Functional Requirements (NFR)

### 5.1 Performance & Scalability
* **NFR-001 (Ingestion Velocity):** The backend ingestion pipeline must sustain a throughput of 5,000 log events per second under peak simulation load without memory leakage.
* **NFR-002 (UI Responsiveness):** All main dashboard widgets and data charts must render within 1.0 second on standard broadband connections.
* **NFR-003 (SOAR Execution Speed):** Automated quarantine execution commands must complete within 500 milliseconds of threat classification.

### 5.2 Security & Data Protection
* **NFR-004 (Data Encryption at Rest & Transit):** All database fields containing sensitive logs or user data must be encrypted using AES-256 at rest; all network communications must enforce TLS 1.3 encryption.
* **NFR-005 (Credential Hashing):** All user passwords must be hashed using `bcrypt` with a minimum cost factor of 12.

### 5.3 Reliability & Availability
* **NFR-006 (System Uptime Target):** The core monitoring engine must achieve 99.9% uptime during academic demonstration cycles.
* **NFR-007 (Graceful AI Fallback):** If external OpenAI API connectivity becomes unavailable, the system must automatically degrade to internal rule-based heuristic scoring without failing or freezing the user interface.

### 5.4 Usability & Brand Compliance
* **NFR-008 (UI Brand Standards):** The user interface must adhere strictly to QIH visual identity standards utilizing Dark Blue (`#0B2545`), Cyan (`#00A8E8`), and White (`#FFFFFF`).
